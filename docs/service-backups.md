# ZOJ 서비스 백업·복구 운영 가이드

중앙 서버 `zoj-app` (`zoj@100.64.0.10`)의 전용 300 GiB scsi1 디스크를
사용합니다. Editor 서버 백업은 별도로 운영하며, 이 문서는 중앙 서버에
설치된 ZOJ 서비스들을 다룹니다.

## 백업 범위

| 대상 | 보관하는 내용 |
| --- | --- |
| PostgreSQL 전체 클러스터 | 계정·패스키·비밀번호 해시, 대회·팀·문제·제출·채점 결과, 공개 상태, 게시글, 작업·감사 기록, 큐, WAL, 권한 |
| MinIO 전체 데이터 볼륨 | 문제 파일, 테스트 입력·정답, 패키지, 코드·검증 산출물, 버킷 설정과 내부 메타데이터 |
| Redis 전체 데이터 볼륨 | AOF/RDB 영속 데이터와 설정 파일 |
| 기타 ZOJ 볼륨 | 실행 중인 Compose 서비스의 마운트, `deploy_` 이름의 볼륨 및 이전 DB 백업 볼륨 |
| 웹 서비스 | `backend-v1`, `frontend`, `test-frontend`의 소스와 실제 배포 파일 |
| 실행 환경 | 실행 중인 모든 ZOJ 서비스의 정확한 Docker 이미지, 프레젠테이션·메일·공지·번들·검증 서비스 설정, 플레이그라운드 실행 이미지 |
| 운영 설정 | 환경 파일, 인증서와 개인키, Nginx, Docker, systemd, cron, 네트워크·SSH·방화벽 설정, Compose 외부 override 파일 |

컨테이너의 명령·환경 변수·포트·마운트도 비공개 복구 자료에 저장합니다.
개인정보와 인증 정보를 포함하므로 저장소는 암호화하며, 원본 설정과 복구
임시 디렉터리는 관리자만 읽을 수 있습니다. Docker 소켓 자체는 백업하지
않습니다. Docker 빌드 캐시·실행 로그, 재생성할 수 있는 컨테이너 계층,
별도 VM의 운영체제는 이 백업 대상이 아닙니다. 채점 에이전트 VM과 외부
프록시·DNS·가상화 호스트는 해당 환경의 복구 절차가 따로 필요합니다.

## 같은 시점의 자료 보관

PostgreSQL·MinIO·Redis와 설정 파일이 모두 같은 ext4 LVM 볼륨에 있는지
확인하고, 임시 16 GiB COW 스냅샷 하나를 만듭니다. LVM이 순간적으로 I/O를
정리하고 스냅샷을 확정하며, 백업 파일은 읽기 전용 스냅샷에서 읽습니다.
애플리케이션과 DB를 정지하지 않습니다. 백업 후 임시 스냅샷을 제거합니다.
데이터가 다른 파일시스템으로 이동하거나 PostgreSQL의 WAL·tablespace가
외부 경로에 생기면 자동으로 중단합니다.

이 방식은 전원이 갑자기 꺼진 시점과 같은 일관성을 보관합니다.
PostgreSQL은 저장된 WAL로 복구하며, Redis는 AOF/RDB를 읽습니다.
서비스 간에 아직 완료되지 않은 작업은 장애 복구 시와 같은 재시도·복구
정책을 따릅니다. Redis 자체의 fsync 정책으로 아직 디스크에 기록되지 않은
데이터까지 보장하는 것은 아닙니다. 백업 간격은 15분이며 연속 시점 복구
(PITR) 기능은 아닙니다.

공유 잠금 `~/zerone-online-judge/service-backup-deploy.lock`으로 정상 배포와
백업을 겹치지 않게 합니다. 백엔드 배포 스크립트, 백엔드·프론트엔드 CI가
같은 잠금을 사용합니다. 서버에서 직접 파일을 수정하는 작업도 이 잠금과
함께 수행해야 배포 파일 전체가 완성된 상태로 보관됩니다.

## 설치

준비된 디렉터리의 파일 해시를 확인한 후 중앙 서버 콘솔에서 한 번 실행합니다.

```bash
sudo bash ~/zoj-maintenance/service-backup-20261025/setup.sh
```

설치기는 호스트 이름, scsi1 고정 장치 경로, 정확히 300 GiB인 빈 디스크,
파티션·파일시스템·시그니처 부재를 확인합니다. 초기화 직전 다시 검사합니다.
기존 자료가 있으면 지우지 않고 중단합니다. 첫 설치 후에는 디스크 UUID로
마운트하며, 재실행해도 포맷하거나 암호화 키를 바꾸지 않습니다.

원본 LVM에는 임시 스냅샷용 미할당 공간이 20 GiB 이상 필요합니다.
운영 볼륨 크기를 변경하거나 서비스를 다른 디스크로 옮긴다면 백업 설계를
다시 점검하십시오. OS 디스크를 수동으로 fsfreeze한 뒤 lvcreate를 실행하는
방식은 사용하지 않습니다.

| 경로 | 용도 |
| --- | --- |
| `/srv/zoj-backup/restic` | 암호화된 백업 저장소 |
| `/srv/zoj-backup/work` | 이미지 캐시·복구 임시 공간, 관리자 전용 |
| `/etc/zoj-backup/config.json` | 원본 LVM·백업 디스크 UUID·범위 설정 |
| `/etc/zoj-backup/repository-password` | 암호화 복구 키 |
| `/var/lib/zoj-backup/status.json` | 비밀번호를 포함하지 않는 운영 상태 |
| `/usr/local/sbin/zoj-backup` | 백업·복구 검사 명령 |

최초 설치는 실제 백업과 격리된 복구 검사를 모두 실행합니다.
성공을 확인하기 전에는 구축 완료로 간주하지 않습니다.

## 주기와 보관 정책

시간은 한국 시간입니다.

- 15분마다 자동 백업, 재부팅 후에도 자동 재개
- 매일 03:40 실제 자료 복구 검사
- 매일 04:40 저장소 검사, 보관 기간 정리 및 공간 회수
- 최근 24시간의 모든 백업, 시간별 72개, 일별 30개, 주별 12개, 월별 12개 보관
- 수동으로 고정한 백업은 자동 삭제하지 않음

정책은 범주별 합집합입니다. 데이터 증가에 따라 사용량이 달라집니다.
복구가 끝나지 않았거나 파일 읽기에 실패한 백업에는 완료 표시를 하지 않으며,
복구 검사에서는 완료된 백업만 선택합니다. 저장소 검사에 실패하면 보관 자료를
삭제하는 단계로 진행하지 않습니다. 백업 디스크가 빠지거나 UUID가 달라지면
OS 디스크에 대신 기록하지 않습니다.

## 상태 확인과 수동 실행

```bash
zoj-backup status
systemctl list-timers 'zoj-backup*'
sudo journalctl -u zoj-backup -u zoj-backup-drill -u zoj-backup-maintain --since today
sudo zoj-backup backup --pin
sudo zoj-backup drill
sudo zoj-backup maintain
```

`health`가 `ok`이고 최근 백업·복구 검사 시각이 갱신되는지 확인합니다.
`failed`는 작업 실패, `stale`은 45분 이상 백업 지연, `unverified`는 48시간
이상 복구 검사가 없음을 뜻합니다. 디스크 사용률 85%부터 `low_space`로
표시합니다. 남은 공간이 5% 또는 10 GiB 미만이면 백업을 중단하며, 복구
검사에는 최소 20 GiB 이상의 여유가 필요합니다. 이미지·문제 파일이 늘면
이보다 더 큰 여유가 필요합니다. 자동으로 외부 메시지를 보내는 구성은
포함하지 않습니다. 상태·서비스 실패와 디스크 용량을 운영 점검에 포함하십시오.

직전 복구 검사 실패는 다음 백업 성공만으로 지워지지 않습니다.
원인을 해결한 후 `sudo zoj-backup drill`의 성공을 확인해야 합니다.
중단된 작업의 임시 스냅샷·검사 컨테이너는 서비스 종료 정리와 다음 작업에서
제거합니다. 운영 컨테이너나 원본 LVM은 정리 대상으로 선택하지 않습니다.

## 매일 실제로 검증하는 내용

1. 완료된 최신 백업을 운영 경로와 분리된 임시 공간에 `--verify`로 복구합니다.
2. 저장한 Docker 이미지의 SHA-256을 확인하고 Docker에 읽어들입니다.
   이미지 ID로 저장하므로 운영 태그를 다른 버전으로 바꾸지 않습니다.
3. 복구 사본의 PostgreSQL을 같은 이미지로 실행해 WAL 복구, 필수 테이블,
   모든 테이블의 개수 및 전체 논리 덤프 읽기를 확인합니다.
4. 복구 사본의 MinIO에서 모든 버킷의 객체를 끝까지 읽어 크기와 SHA-256을
   계산하고, DB에 있는 문제·테스트·검증 파일 참조가 존재하는지 확인합니다.
5. 복구 사본의 Redis가 AOF/RDB를 읽고 응답하는지 확인합니다.
6. 개수·검증한 파일 수·용량·백업 ID를 상태 파일에 남기고 임시 자료를 지웁니다.

검사 컨테이너는 외부 네트워크와 공개 포트가 없습니다. MinIO 검사 도구만
해당 격리 컨테이너의 네트워크를 공유하며, 운영 볼륨·Docker 소켓을 마운트하지
않습니다. 메일·공지·검증·채점 작업 소비자는 실행하지 않으므로 복구 검사가
메일이나 채점 작업을 재발송하지 않습니다. 이 검사는 저장 자료와 핵심 저장
서비스의 복구를 검증하며, 실제 사용자 로그인과 외부 DNS까지 자동 시험하는
전체 장애 전환 훈련을 대신하지는 않습니다.

## 장애 시 복구 절차

아래 작업은 **새 복구 서버 또는 중지된 서비스**에서 수행합니다.
운영 경로에 바로 복구하거나 라이브 DB 위에 덮어쓰지 마십시오.

1. 백업 디스크 또는 복제한 저장소와 서버 밖에 보관한 복구 키를 준비합니다.
2. Restic을 설치하고 별도 경로에 복구합니다.

   ```bash
   export RESTIC_REPOSITORY=/srv/zoj-backup/restic
   export RESTIC_PASSWORD_FILE=/secure/recovery.key
   sudo -E restic snapshots --tag zoj-services-complete-v1
   sudo -E restic restore SNAPSHOT_ID --target /srv/zoj-recovery --verify
   ```

3. `/srv/zoj-recovery/var/lib/zoj-backup/catalog/manifest.json`과
   `runtime-inspect.json`에서 원래 경로·이미지 ID·서비스 구성을 확인합니다.
   자료 본체는 복구 디렉터리 아래의 `var/lib/zoj-backup/snapshot/`에 있습니다.
   PostgreSQL의 `pg_wal`을 포함한 전체 데이터, MinIO의 숨김 메타데이터,
   Redis의 appendonly 디렉터리를 반드시 함께 복원합니다.
4. 이미지 아카이브를 `docker load -i ...`로 읽어들이고 **저장된 이미지 ID**로
   서비스를 고정합니다. `latest` 태그나 다른 PostgreSQL 메이저 버전으로
   먼저 실행하지 마십시오. Compose 파일의 원래 상대 경로와 외부 override도
   복원합니다. root가 소유자·권한을 보존하여 파일을 배치해야 합니다.
5. 운영 Compose·메일·공지·채점 소비자를 중지한 채 복구 사본으로 DB·MinIO·
   Redis를 먼저 점검합니다. 복구한 DB의 오래된 `postmaster.pid`만 제거할 수
   있으며 운영 DB의 PID 파일을 제거해서는 안 됩니다.
6. DB·파일 참조와 대회·제출 기록을 확인한 후 API·Nginx를 시작하고 로그인,
   문제 조회, 제출 기록을 확인합니다. 진행 중이던 작업·메일 큐는 운영자가
   중복 처리 여부를 점검한 다음 소비자를 재개합니다. 외부 에이전트의
   연결·lease와 프록시·DNS·인증서도 함께 확인합니다.
7. 새 서버의 데이터 경로·LVM UUID·백업 디스크 UUID에 맞춰 백업 설정을 다시
   구성하고 첫 백업 및 복구 검사 성공을 확인합니다. SSH·네트워크 설정은
   새 서버에 맞게 검토하고, Tailscale·배포 러너는 필요하면 다시 등록합니다.

완료 표시가 없는 스냅샷은 정상 복구 후보로 선택하지 않습니다.
문제별·대회별 복원은 먼저 별도 DB·MinIO에 전체 복구한 뒤 필요한 자료를
검토하여 이관하는 방식으로 수행하십시오.

## 복구 키와 서버 외부 사본

설치 시 `~/zoj-backup-recovery.key`에 관리자용 사본을 만듭니다.
키 내용을 채팅·Git·운영 로그에 붙여 넣지 말고, 다른 기기나 비밀번호
관리자에 보관하십시오. 키를 잃으면 암호화된 백업을 복구할 수 없습니다.

추가 디스크는 원본 디스크 장애·오삭제·잘못된 변경에 대비하는 로컬 백업입니다.
같은 가상화 호스트 전체 장애나 관리자 권한 탈취에 대비하려면 저장소의
**별도 서버 또는 오프라인 사본**도 필요합니다. 복제할 때는 모든 백업 작업을
공유 잠금으로 멈춘 상태에서 저장소 전체를 복사하거나 Restic의 다른 저장소
복사 기능을 사용하고, 복제본에서도 복구 검사를 수행하십시오. 별도 저장소의
목적지가 정해지기 전에는 임의의 외부 서비스로 자료를 전송하지 않습니다.
